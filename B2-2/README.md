# AI 뉴스 요약 자동화 시스템

> **TechCrunch RSS를 활용하여 최신 AI 및 기술 뉴스를 자동으로 수집하고, 생성형 AI(DeepSeek)를 이용해 핵심 내용을 요약한 뒤 Notion 데이터베이스에 자동 저장하는 뉴스 자동화 시스템**

---

# 1. 프로젝트 개요

## 1.1 프로젝트 목적

최근 생성형 AI와 IT 산업은 매우 빠르게 변화하고 있으며, 새로운 기술과 서비스가 하루에도 수십 건 이상 발표되고 있다. 이러한 정보를 빠르게 파악하기 위해서는 TechCrunch와 같은 기술 뉴스 사이트를 지속적으로 확인해야 하지만, 매번 사이트를 방문하여 새로운 기사를 확인하고 내용을 읽은 뒤 필요한 내용을 정리하는 과정은 많은 시간이 소요된다.

특히 여러 뉴스 사이트를 동시에 관리하거나 팀 단위로 최신 기술 동향을 공유해야 하는 경우에는 단순히 뉴스를 읽는 것보다 **뉴스를 수집하고 정리하는 작업 자체가 더 많은 시간을 차지**하게 된다.

본 프로젝트에서는 이러한 반복 작업을 자동화하기 위해 **Make**를 이용하여 RSS 뉴스 수집부터 AI 요약, Notion 저장까지 하나의 자동화 파이프라인으로 구성하였다.

또한 단순히 뉴스를 저장하는 것에서 끝나는 것이 아니라 **중복 기사 저장 방지**, **AI API 호출 최소화**, **자동 실행**, **예외 처리** 등을 함께 구현하여 실제 운영 가능한 뉴스 자동화 시스템을 구축하는 것을 목표로 하였다.

프로젝트를 통해 반복적인 뉴스 수집 업무를 자동화하고, 사람이 직접 수행해야 하는 작업을 최소화하여 보다 효율적인 정보 관리 환경을 구축하고자 하였다.

---

## 1.2 프로젝트 배경

최근 대부분의 기업에서는 생성형 AI와 자동화 기술을 이용하여 반복적인 업무를 줄이고 있다.

특히 뉴스 수집 업무는 다음과 같은 문제점을 가지고 있다.

- 여러 뉴스 사이트를 직접 방문해야 한다.
- 새로운 기사가 올라왔는지 지속적으로 확인해야 한다.
- 필요한 기사만 선별해야 한다.
- 기사 내용을 읽고 핵심 내용을 다시 정리해야 한다.
- 팀원들과 공유하기 위해 별도의 협업 도구에 저장해야 한다.

이러한 작업은 단순하지만 반복적으로 수행되어야 하므로 자동화의 효과가 매우 큰 업무이다.

RSS는 새로운 게시글이 등록될 때마다 최신 정보를 제공하기 때문에 별도의 크롤링을 수행하지 않아도 안정적으로 최신 뉴스를 수집할 수 있다.

또한 최근에는 생성형 AI가 긴 문서를 짧은 문장으로 요약하는 능력이 크게 향상되었기 때문에, AI를 이용하면 기사의 핵심 내용만 빠르게 확인할 수 있다.

따라서 본 프로젝트에서는

**RSS → AI 요약 → Notion 저장**

이라는 자동화 구조를 설계하여 최신 기술 뉴스를 사람이 개입하지 않아도 자동으로 관리할 수 있는 시스템을 구현하였다.

## 1.3 사용 기술

본 프로젝트에서 사용한 기술은 다음과 같다.

| 기술 | 사용 목적 |
|------|-----------|
| Make | 전체 자동화 워크플로우 구성 |
| TechCrunch RSS | 최신 기술 뉴스 수집 |
| HTTP Module | OpenRouter API 호출 |
| OpenRouter | DeepSeek API 제공 |
| DeepSeek Chat | 뉴스 요약 |
| Notion | 뉴스 데이터 저장 |
| Data Store | 중복 기사 관리 |
| Filter | 중복 기사 판별 |
| Scheduler | 매일 자동 실행 |

각 기술을 선택한 이유는 다음과 같다.

### Make

Make는 다양한 서비스를 코드 작성 없이 연결할 수 있는 자동화 플랫폼이다.

RSS, HTTP, Notion 등 다양한 서비스를 하나의 시나리오로 연결할 수 있으며, 조건문(Filter), Data Store, Scheduler 등을 제공하기 때문에 본 프로젝트의 자동화 구조를 구현하기에 적합하였다.

### TechCrunch RSS

TechCrunch는 최신 IT 및 AI 뉴스를 빠르게 제공하는 대표적인 기술 뉴스 사이트이다.

RSS Feed를 제공하기 때문에 크롤링 없이 안정적으로 최신 뉴스 정보를 받아올 수 있으며, 저작권 문제 없이 RSS 표준을 이용할 수 있다는 장점이 있다.

### OpenRouter + DeepSeek

뉴스 요약에는 OpenRouter를 통해 DeepSeek Chat 모델을 사용하였다.

OpenRouter를 이용하면 다양한 생성형 AI 모델을 동일한 API 형식으로 사용할 수 있으며, DeepSeek 모델은 긴 뉴스 기사도 비교적 정확하게 요약하는 성능을 보여주었다.

### Notion

요약된 뉴스를 저장하기 위한 협업 도구로 Notion을 선택하였다.

Notion은 데이터베이스 형태로 정보를 관리할 수 있으며 제목, 요약문, URL, 발행일 등을 각각의 속성으로 저장할 수 있어 뉴스 관리에 적합하였다.

### Data Store

Make의 Data Store는 이미 처리한 기사를 저장하기 위해 사용하였다.

RSS에서 동일 기사가 다시 전달되는 경우 AI API를 다시 호출하지 않도록 중복 여부를 판단하는 역할을 수행한다.

# 2. 시스템 구성

## 2.1 전체 워크플로우

본 프로젝트에서 구현한 전체 자동화 구조는 다음과 같다.

```text
Scheduler
     │
     ▼
RSS Feed
     │
     ▼
Data Store 조회
     │
     ▼
Filter (중복 여부 확인)
     │
     ▼
HTTP(OpenRouter)
     │
     ▼
Notion 저장
     │
     ▼
Data Store 업데이트
```

위 구조는 **기사 수집 → 중복 검사 → AI 요약 → 저장 → 기록**의 순서로 동작한다.

동일한 기사를 다시 처리하지 않도록 AI 호출 전에 반드시 Data Store를 먼저 조회하도록 설계하였다.

## 2.2 사용한 모듈 설명

### RSS

TechCrunch RSS Feed에서 최신 뉴스 정보를 가져오는 모듈이다.

가져오는 데이터는 다음과 같다.

- 기사 제목
- 기사 링크
- GUID
- 발행일
- 기사 본문

RSS는 프로젝트의 시작점으로 사용되며 모든 뉴스 데이터는 이 모듈을 통해 전달된다.

---

### Data Store

Data Store는 이미 처리한 기사를 저장하는 역할을 수행한다.

RSS의 GUID(URL)를 Key 값으로 저장하여 중복 여부를 판단하였다.

Data Store는 다음과 같은 순서로 동작한다.

1. RSS GUID 조회
2. Data Store 검색
3. 존재하면 종료
4. 존재하지 않으면 다음 단계 진행

이를 통해 동일 기사에 대한 AI 호출을 방지하였다.

---

### HTTP

HTTP 모듈은 OpenRouter API를 호출하기 위해 사용하였다.

기사 제목과 본문을 JSON 형태로 전달하고 DeepSeek 모델이 3줄 이내의 요약을 생성하도록 프롬프트를 작성하였다.

---

### Notion

AI가 생성한 요약을 저장하는 데이터베이스이다.

다음 속성들을 저장하도록 설계하였다.

- UUID
- 제목
- 요약
- 원문 링크
- 발행일
- Source

---

## 2.3 데이터 흐름

데이터는 아래와 같은 흐름으로 전달된다.

1. RSS가 최신 뉴스 데이터를 가져온다.
2. RSS의 GUID(URL)를 Data Store에서 조회한다.
3. Data Store에 존재하지 않는 경우에만 Filter를 통과한다.
4. HTTP 모듈이 OpenRouter API를 호출하여 DeepSeek 모델에 기사 내용을 전달한다.
5. 생성된 요약을 Notion 데이터베이스에 저장한다.
6. 저장이 완료되면 Data Store에 GUID를 기록하여 다음 실행 시 중복되지 않도록 한다.

이와 같은 구조를 통해 동일 뉴스에 대한 AI API 호출을 방지하면서도 새로운 기사만 자동으로 저장하도록 구현하였다.

# 3. Make 구현 과정

본 프로젝트의 핵심은 여러 서비스를 하나의 자동화 파이프라인으로 연결하는 것이었다.

초기에는 RSS에서 가져온 기사를 바로 AI에 전달한 후 Notion에 저장하는 단순한 구조를 설계하였다.

그러나 테스트를 진행하는 과정에서 RSS는 동일 기사를 여러 번 반환할 수 있다는 점을 확인하였고, 동일 뉴스에 대해 AI API가 반복 호출되는 문제가 발생하였다.

또한 Notion 자체에서는 UUID의 중복을 막을 수 없었기 때문에 새로운 중복 방지 구조가 필요하였다.

이러한 문제를 해결하기 위해 RSS → Data Store → Filter → HTTP → Notion → Data Store Update 구조로 개선하였다.

---

## 3.1 RSS 모듈 구현

RSS 모듈은 TechCrunch에서 제공하는 RSS Feed를 이용하여 최신 뉴스를 자동으로 수집하도록 구성하였다.

RSS Feed URL은 다음과 같다.

```
https://techcrunch.com/feed/
```

RSS 모듈에서는 기사의 제목, 링크, GUID, 발행일, 본문 등을 함께 가져올 수 있도록 설정하였다.

가져온 데이터는 이후 모든 모듈에서 공통적으로 사용되기 때문에 프로젝트의 시작점 역할을 수행한다.

RSS는 Scheduler와 연결되어 매일 자동으로 실행되도록 구성하였다.

---

## 3.2 Data Store 구현

초기에는 Notion에서 UUID를 관리하여 중복 저장을 막으려고 하였으나 Notion은 UNIQUE 제약조건을 지원하지 않아 동일한 UUID도 계속 저장되는 문제가 발생하였다.

이를 해결하기 위해 Make의 Data Store를 도입하였다.

Data Store에는 RSS의 GUID(URL)를 Key 값으로 저장하였다.

새로운 뉴스가 들어오면 가장 먼저 Data Store에서 동일한 Key가 존재하는지 조회하도록 구성하였다.

Key가 존재하지 않는 경우에만 다음 단계가 실행되도록 설계하였다.

# 4. 구현 과정에서 발생한 문제 및 해결

프로젝트를 진행하면서 가장 어려웠던 부분은 단순히 RSS와 Notion을 연결하는 것이 아니라, **실제 운영 가능한 자동화 시스템을 구현하는 과정**이었다.

초기에는 RSS에서 뉴스를 가져와 AI에게 요약을 요청한 뒤 Notion에 저장하는 단순한 구조를 설계하였다.

그러나 실제 테스트를 진행하면서 중복 저장, API 호출 비용 증가, Notion API 변경, 인증 오류 등 다양한 문제가 발생하였다.

본 장에서는 프로젝트를 구현하면서 발생한 문제와 해결 과정을 순서대로 설명한다.

---

## 4.1 Notion UUID 중복 저장 문제

처음에는 동일한 뉴스가 여러 번 저장되는 문제를 해결하기 위해 Notion 데이터베이스에 UUID 속성을 추가하였다.

RSS Feed에서 제공하는 GUID(URL)를 UUID 컬럼에 저장하면 동일한 값이 존재할 경우 새로운 데이터가 생성되지 않을 것이라고 예상하였다.

하지만 여러 차례 테스트를 진행한 결과, 동일한 UUID 값을 가진 데이터도 계속 생성되는 현상을 확인하였다.

이는 일반적인 관계형 데이터베이스(MySQL, PostgreSQL 등)와 달리 Notion은 PRIMARY KEY 또는 UNIQUE 제약조건을 지원하지 않기 때문이다.

즉,

동일한 UUID를 가진 페이지라도 Notion에서는 새로운 페이지로 인식하여 계속 저장하였다.

초기에는 Search Objects 기능을 이용하여 UUID를 검색하는 방법도 고려하였다.

그러나 Search Objects는 페이지 제목이나 객체 자체를 검색하는 기능이며 데이터베이스 내부 특정 속성을 기준으로 검색하는 기능은 제공하지 않았다.

또한 Query Data Source 기능도 사용하려고 하였으나 현재 사용 중인 Make 버전에서는 해당 기능이 제공되지 않았다.

결국 Notion 내부에서 중복 여부를 검사하는 방식은 구현이 어렵다고 판단하였다.

따라서 중복 여부는 Notion이 아닌 Make 내부에서 관리하도록 구조를 변경하였다.

---

## 4.2 Data Source ID 오류

프로젝트 초기에 Notion 모듈을 설정하는 과정에서 다음과 같은 오류가 발생하였다.

```
body.parent.page_id should be defined

body.parent.database_id should be defined

body.parent.data_source_id should be a valid uuid
```

처음에는 Database ID를 입력하면 정상적으로 동작할 것이라고 생각하였다.

하지만 최근 Notion API에서는 기존 Database 중심 구조에서 Data Source 구조로 변경되었기 때문에 Database ID만으로는 데이터를 생성할 수 없었다.

Database URL에서 확인한 ID와 실제 Data Source ID가 서로 다르다는 사실도 구현 과정에서 확인하였다.

처음에는 Data Source ID를 찾는 방법을 몰라 여러 차례 Validation Error가 발생하였다.

결국 Notion의

Manage Data Sources

메뉴에서 Data Source ID를 복사하여 입력하는 방식으로 문제를 해결하였다.

이후 Notion 모듈은 정상적으로 동작하였으며 데이터 저장도 성공하였다.

이번 경험을 통해 최근 Notion API 변경 사항을 확인하는 것이 매우 중요하다는 점을 알 수 있었다.

---

## 4.3 HTTP(OpenRouter) 인증 오류

뉴스 요약에는 OpenRouter를 통해 DeepSeek Chat 모델을 사용하였다.

Make에는 OpenRouter 전용 모듈이 존재하지 않았기 때문에 HTTP 모듈을 직접 구성해야 했다.

초기에는 API URL만 입력하면 동작할 것이라고 생각하였으나 계속해서 인증 오류가 발생하였다.

원인은 HTTP Header 설정이 올바르지 않았기 때문이다.

처음에는 Authorization Header가 누락되어 있었고

Bearer

문자열 없이 API Key만 입력하여 계속 인증이 실패하였다.

또한 Content-Type이 application/json으로 설정되지 않아 Body가 정상적으로 전달되지 않는 문제도 발생하였다.

최종적으로 다음과 같이 설정하였다.

- Authorization : Bearer API_KEY
- Content-Type : application/json
- HTTP-Referer : make.com

그리고 Body를 JSON 형태로 직접 작성하여

기사 제목

기사 내용

요약 조건

## 4.4 동일 기사에 대해 AI가 반복 호출되는 문제

RSS Feed는 항상 새로운 기사만 반환하는 것이 아니라 기존 기사도 함께 반환할 수 있었다.

특히 생성형 AI API는 호출 횟수에 따라 비용이 발생하기 때문에 이러한 구조는 실제 서비스에서는 매우 비효율적이었다.

동일 기사에 대해 계속 API를 호출하는 것은

비용 증가

처리 시간 증가

불필요한 토큰 사용

이라는 문제를 발생시켰다.

따라서 HTTP 모듈을 실행하기 전에 반드시 중복 여부를 검사해야 한다고 판단하였다.

이를 통해 외부에 인증 정보가 노출되지 않도록 보안을 강화하였다.

```
# 7. 에러 처리 정책

자동화 시스템은 사람이 직접 확인하지 않아도 안정적으로 동작해야 하므로 다양한 예외 상황을 고려하여 설계하였다.

## 7.1 RSS 수집 실패

RSS Feed에서 새로운 기사가 존재하지 않거나 네트워크 문제로 데이터를 가져오지 못하는 경우에는 다음 단계를 수행하지 않고 시나리오를 종료하도록 하였다.

이를 통해 빈 데이터를 AI에게 전달하는 문제를 방지하였다.

---

## 7.2 중복 기사 처리

Data Store에서 동일한 GUID가 확인되면 해당 기사는 이미 처리한 기사로 판단하였다.

이 경우 Filter에서 즉시 종료하도록 설정하였다.

이를 통해

- HTTP 호출 방지
- AI API 비용 절감
- Notion 중복 저장 방지

를 동시에 수행하였다.

---

## 7.3 HTTP 요청 실패

OpenRouter API 호출 과정에서 인증 오류 또는 일시적인 네트워크 오류가 발생할 수 있다.

이 경우 Make의 Error Handling 기능을 이용하여 최대 **2회까지 재시도**하도록 설계하였다.

2회 재시도 이후에도 실패하는 경우에는 해당 기사를 건너뛰고 다음 실행에서 다시 처리하도록 하였다.

이는 과제에서 요구하는 **"기사 1건당 최대 2회 재시도"** 조건을 만족하도록 구성한 것이다.

---

## 7.4 Notion 저장 실패

Notion API 오류나 일시적인 네트워크 문제로 저장이 실패하는 경우에는 Data Store를 업데이트하지 않도록 설계하였다.

만약 저장이 실패했는데 Data Store만 업데이트된다면 다음 실행에서 해당 기사를 이미 처리한 기사로 인식하게 된다.

이를 방지하기 위해

Notion 저장 성공

↓

Data Store Update

순서를 유지하였다.

---

API Key와 Notion Connection 정보는 Make 내부 Connection 기능을 이용하여 관리하였다.

README와 발표 자료에 포함되는 모든 스크린샷에서는 API Key가 노출되지 않도록 마스킹 처리하였다.
```

```
# 8. 비용 절감 및 중복 저장 방지

자동화 시스템에서는 생성형 AI API 호출 비용이 지속적으로 발생하기 때문에 불필요한 API 호출을 줄이는 것이 매우 중요하다.

새로운 기사가 들어오면 가장 먼저 Data Store를 조회하여 동일 Key가 존재하는지 확인하였다.

이미 존재하는 경우에는 HTTP 모듈을 실행하지 않고 즉시 종료하였다.
```


# 9. 실행 결과

본 프로젝트에서는 Make를 이용하여 **RSS 뉴스 수집 → 생성형 AI 요약 → Notion 자동 저장**까지의 모든 과정을 자동으로 수행하는 뉴스 자동화 시스템을 구현하였다.

최종 워크플로우는 Scheduler를 시작으로 RSS Feed에서 최신 뉴스를 수집하고, Data Store를 이용하여 이미 처리한 기사인지 확인한 뒤 새로운 기사인 경우에만 DeepSeek API를 호출하여 요약을 생성하였다. 이후 생성된 요약은 Notion 데이터베이스에 자동 저장되며, 마지막으로 Data Store를 업데이트하여 다음 실행에서 동일 기사가 다시 처리되지 않도록 설계하였다.

프로젝트의 모든 단계는 사람의 개입 없이 자동으로 수행되며, Make의 Scheduler를 이용하여 지정한 시간마다 자동 실행되도록 설정하였다.

---

## 9.1 최종 워크플로우

최종적으로 구현한 자동화 구조는 다음과 같다.

```
Scheduler

↓

RSS Feed

↓

Data Store

↓

Filter

↓

HTTP(OpenRouter)

↓

Notion

↓

Data Store Update
```

이 구조를 적용함으로써

- 뉴스 자동 수집
- AI 자동 요약
- 자동 저장
- 중복 저장 방지

까지 하나의 자동화 파이프라인으로 연결하였다.

---

## 9.2 실행 결과

실제 테스트에서는 TechCrunch RSS에서 최신 기술 뉴스를 정상적으로 가져오는 것을 확인하였다.

RSS에서 전달된 기사 제목과 본문은 HTTP 모듈을 통해 DeepSeek 모델로 전달되었으며, 생성된 요약은 Notion 데이터베이스에 자동 저장되었다.

저장된 데이터에는 다음과 같은 정보가 포함되었다.

|속성|저장 결과|
|---|---|
|기사 제목|정상 저장|
|AI 요약|정상 생성|
|원문 링크|정상 저장|
|발행일|정상 저장|
|UUID(GUID)|정상 저장|
|Source|정상 저장|

## 9.3 중복 저장 테스트

프로젝트에서 가장 중요하게 테스트한 부분은 동일 기사의 중복 저장 여부였다.

동일한 RSS를 여러 번 실행하여 반복 테스트를 수행하였다.

테스트 결과

첫 번째 실행에서는

```
RSS

↓

Data Store 조회

↓

없음

↓

HTTP 실행

↓

Notion 저장

↓

Data Store 저장
```

순서로 정상 동작하였다.

두 번째 실행에서는

```
RSS

↓

Data Store 조회

↓

이미 존재

↓

Filter 종료
```

로 처리되어 HTTP 모듈이 실행되지 않았다.

따라서

- 동일 기사 중복 저장 없음
- AI API 재호출 없음
- Notion 중복 데이터 없음

을 확인하였다.

## 9.4 프로젝트 성과

최종적으로 구현한 시스템은 과제에서 요구한 모든 기능을 만족하였다.

### 데이터 수집

- RSS Feed를 이용하여 최신 기술 뉴스 자동 수집

### AI 가공

- DeepSeek를 이용한 3줄 이내 뉴스 요약

### 자동 저장

- Notion 데이터베이스 자동 저장

### 자동 실행

- Scheduler를 이용한 자동 실행

### 중복 저장 방지

- Data Store 기반 중복 검사

### 비용 절감

- 동일 기사에 대한 AI 호출 제거

### 에러 처리

- 최대 2회 재시도
- 중복 기사 Skip
- Notion 저장 순서 보장

결과적으로 사람이 직접 뉴스를 확인하지 않아도 최신 AI 뉴스를 자동으로 수집하고 요약하여 Notion에 저장하는 자동화 시스템을 성공적으로 구현하였다.

# 결론

본 프로젝트에서는 Make를 이용하여 RSS 기반 뉴스 자동화 시스템을 구현하였다.

RSS Feed를 통해 최신 기술 뉴스를 자동으로 수집하고, OpenRouter를 통해 DeepSeek 생성형 AI 모델이 핵심 내용을 요약한 뒤, Notion 데이터베이스에 자동 저장하는 전체 자동화 파이프라인을 구축하였다.

프로젝트를 구현하는 과정에서 Notion의 UUID 중복 문제, Data Source ID 변경, HTTP 인증 오류, 동일 기사 반복 저장 등 다양한 문제를 경험하였으며, 이를 해결하기 위해 Data Store 기반의 중복 검사 구조를 설계하였다.

특히 Data Store를 이용하여 동일 기사에 대한 AI API 호출을 차단함으로써 API 비용을 절감하고, Notion 데이터베이스의 중복 저장을 방지하는 안정적인 구조를 완성하였다.

이번 프로젝트를 통해 RSS 데이터 수집, 생성형 AI 활용, API 연동, 자동화 워크플로우 설계, 예외 처리 및 데이터 관리 방법을 실제로 구현해 볼 수 있었으며, 단순한 자동화 기능 구현을 넘어 실제 운영 가능한 자동화 시스템을 설계하는 경험을 얻을 수 있었다.

향후에는 다중 RSS 지원, AI 기반 기사 분류, 이미지 생성, 감성 분석, Discord 및 이메일 알림 등 다양한 기능을 추가하여 보다 완성도 높은 뉴스 자동화 플랫폼으로 발전시킬 계획이다.
